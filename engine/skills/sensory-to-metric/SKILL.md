# 把「感官验收」翻译成「可测量的指标」

## 为什么需要这一套

当前模型**没有视觉/听觉输入**。但一半以上的任务成果是给眼睛看的：
3D 模型、封面图、视频、网页、图表、PPT。

看不了，就只能：

- 靠猜 → 交付十个坏结果
- 或者不交 → 干脆不做

真机日志里的原话：

> 自己检查质量！为啥树都是浮空的 还有也太粗糙了吧！！

「浮空」和「粗糙」都是**一眼能看出的问题**。它们之所以漏到用户那里，
是因为没有把它们变成**代码能查的东西**。

## 通用四步法

### 第 1 步：把「好」拆成可判定的属性

用户说「精致」「好看」「专业」——这些词不能执行。拆开：

| 模糊的话 | 拆成可判定的 |
|---|---|
| 精致 / 有细节 | 颜色数 > 5000；面数 5 万–200 万；有材质贴图 |
| 不粗糙 | 边缘锯齿 < X；材质反射率非零；有 AO/阴影 |
| 浮空 | 每个物体最低点 \|z\| < 0.01 |
| 比例正常 | 门高 2m ±10%；层高 3m ±20% |
| 布局不乱 | 元素间距 > 8px；无重叠；对齐到栅格 |
| 颜色协调 | 主色 ≤ 3 种；饱和度方差 < X |
| 视频流畅 | 帧率 ≥ 24；无丢帧；音画偏差 < 50ms |
| 声音不炸 | 峰值 ≤ -1dBFS；LUFS -14 ±2 |

**拆完必须有数字或布尔值。** 拆不出数字的，说明还没想清楚。

### 第 2 步：为每条指标写一个「能失败」的检查

**关键：检查必须真的会失败。** 永远返回 OK 的检查等于没有。

```python
def check_ground(objs, eps=0.01):
    bad = [(o.name, lowest_z(o)) for o in objs if abs(lowest_z(o)) > eps]
    return bad          # 非空就是失败
```

写完后**故意造一个坏的样例**跑一遍，确认它真能报错。
真机上的教训：我写的指标检查一开始全是 0 失败，后来发现是解析 bug。

### 第 3 步：分级——哪些必须过，哪些是加分

不是所有指标都同等重要。

| 级别 | 含义 | 处理 |
|---|---|---|
| **阻断级** | 不合规 = 明显是坏的（浮空、穿模、全白、黑屏） | **不合格不准交付** |
| **质量级** | 达不到 = 「不够精致」 | 报告给用户，让他决定 |
| **参考级** | 仅供对比 | 只记录 |

把「浮空」放阻断级，「颜色数」放质量级——前者是错，后者是程度。

### 第 4 步：交付时把指标连同结论一起说

不要只说「做好了」。要说：

> 房子建好了。自检：12 个物体全部贴地，最大面数 18 万，材质齐全。
> 渲染用了 4 分 20 秒/帧。
> **但我看不了画面**——如果构图或配色不对，你告诉我哪里，我按坐标改。

**最后那句很重要。** 它诚实说明了「我没验的部分」，用户知道该看什么。

## 终局方案：让电脑自己看图

前面那些指标（颜色数、拉普拉斯方差）只是**近似**。真机的最终解是：

> **在用户电脑上跑一个本地视觉模型（Qwen2.5-VL-7B Q4 + Ollama），
> 让它看图并给分，把「8/10」这样的判定回传给手机。**

真机日志里的实际交付说明：

```
UP主房间 3D 场景（Godot 4.3 渲染）—— 本地视觉模型评为 8/10
```

**这条链路解决了「模型没有视觉输入」的根本困境：**
不是让手机看懂图，而是**让电脑看完把结论告诉手机**。

### 怎么搭

```sh
# 电脑上（一次性）
# 1. Ollama 免安装版放到 D:\ollama
# 2. 拉视觉模型 + 投影层
ollama pull qwen2.5-vl:7b
# 3. 验证
ollama run qwen2.5-vl:7b "描述这张图" --image D:\shot.png
```

### 怎么用（每次验收）

```sh
# 1. 生成截图（3D 场景必须用引擎内部截屏，见下）
pc.mjs ps "godot --script capture.gd"

# 2. 取回或直接在电脑上评分
pc.mjs ps "ollama run qwen2.5-vl:7b '给这张图打分（1-10），并指出最明显的三个缺点' --image D:\shot.png"
```

### 评分的用法

**不要只问「好不好看」**，要问结构化的问题：

| 问法 | 得到 |
|---|---|
| ❌「这张图好看吗」 | 「很好看」（无信息） |
| ✅「1-10 分，并列出三个最明显的问题」 | 「8/10；①左下角地面接缝 ②窗户过曝 ③人物比例偏大」 |

**后面那三个问题就是下一轮的修改清单。**

### 门槛

```
< 6/10   → 不许交付，回去改
6-8/10   → 可以给用户看，说明还差什么
> 8/10   → 可以交付
```

**打分的人和生成的人要分开**（同一个模型自评容易自我肯定）。

## 3D / GPU 窗口截图：必须用引擎内部截屏

真机日志的教训：

> 抓 3D/GPU 渲染窗口的截图，外部 API 全部不可靠，必须用引擎内部截屏

**为什么**：`CopyFromScreen` 抓的是桌面合成后的画面。当 3D 程序用独立全屏
或独占全屏时，桌面合成层没有内容，抓到的是黑屏或残留。

### 各引擎的正确做法

| 引擎 | 怎么截 |
|---|---|
| **Godot 4** | `get_viewport().get_texture().get_image().save_png(path)` |
| **Blender** | `bpy.context.scene.render.filepath=...; bpy.ops.render.render(write_still=True)` |
| **Unity** | `ScreenCapture.CaptureScreenshot(path)` |
| **WebGL / three.js** | `renderer.domElement.toDataURL()`（注意 `preserveDrawingBuffer: true`） |

**统一原则：让渲染它的人来截，不要让外部去抓。**

## 按领域的对照表

### 3D / Blender

| 指标 | 怎么算 | 级别 |
|---|---|---|
| 贴地 | 所有 mesh 最低点 \|z\| < 0.01 | 阻断 |
| 穿模 | 包围盒三轴相交 > 5% 最小边 | 阻断 |
| 面数 | 总和 < 200 万 | 阻断 |
| 有材质 | 每个 mesh 至少一个 material | 阻断 |
| 细节 | 渲染图唯一颜色数 > 5000 | 质量 |
| 光照 | 平均亮度 60–200（0–255） | 质量 |
| 构图 | 主体占画面 20%–70% | 质量 |

### 网页 / UI

| 指标 | 怎么算 | 级别 |
|---|---|---|
| **无横向溢出** | `scrollWidth <= clientWidth` | 阻断 |
| 文字不溢出容器 | 所有元素 `scrollHeight <= clientHeight` | 阻断 |
| 无重叠 | 两两元素矩形不相交 | 阻断 |
| 对齐 | 左边缘 x 坐标落在 8px 栅格上 | 质量 |
| 对比度 | WCAG AA ≥ 4.5:1 | 质量 |
| 响应式 | 375 / 768 / 1440 三档都不溢出 | 质量 |

**用无头浏览器跑**：`page.evaluate()` 拿 `scrollWidth` 和 `getBoundingClientRect()`。
比截图给人看有效得多——真机日志里「右边都超出范围了」被指出过 3 次。

### 图片 / 封面

| 指标 | 怎么算 | 级别 |
|---|---|---|
| 不是纯色 | 唯一颜色数 > 1000 | 阻断 |
| 不糊 | 拉普拉斯方差 > 100（清晰度） | 质量 |
| 不过曝 | 255 像素占比 < 5% | 质量 |
| 不过暗 | <10 像素占比 < 10% | 质量 |
| 构图 | 主体检测框占 20%–80% | 质量 |

### 视频

| 指标 | 怎么算 | 级别 |
|---|---|---|
| 帧数完整 | `ffprobe` 帧数 == 预期 | 阻断 |
| 无坏帧 | 每帧能解码 | 阻断 |
| 音画同步 | 音频/视频起点差 < 50ms | 阻断 |
| 帧率 | ≥ 24fps | 质量 |
| 亮度 | 平均 40–200 | 质量 |
| 无黑帧 | 连续全黑帧 < 2 | 质量 |

### 音频 / TTS

| 指标 | 怎么算 | 级别 |
|---|---|---|
| 不静音 | RMS > -40dBFS | 阻断 |
| 不削波 | 峰值 ≤ -1dBFS | 阻断 |
| 响度 | LUFS -14 ± 2（`ffmpeg -af loudnorm`） | 质量 |
| 语速 | 每秒字数为 3–6 | 质量 |

## 三条铁律

1. **每条指标都要能失败。** 写完后故意造坏样例验证一次。永远绿的检查是装饰。
2. **阻断级不过就不许说「做好了」。** 宁可说「自检没过，卡在 X」。
3. **交付时说明「我没验的部分」。** 你看不了图这件事要主动讲，别让用户以为你验过了。

## 常见坑

**坑 1：指标太宽松，等于没查。**
「颜色数 > 100」——纯色块也有 100 种。要定到能区分好坏的值。

**坑 2：只查自己会做的。**
「我能算出面数，就只查面数」。但用户在意的是构图和配色。
**先从用户抱怨里反推指标**，不是从自己的工具箱出发。

**坑 3：把「检查通过」当成「好看」。**
检查只能保证「不是明显的坏」。好看是主观的，最终要靠用户。
**所以交付时要说清楚哪些是自检保证的、哪些需要他判断。**
